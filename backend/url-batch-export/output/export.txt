Redis 개요	이 글은 Redis 공식 문서를 읽으며, 주요 개념을 중심으로 추가 조사와 개인적인 이해를 덧붙여 정리한 기록입니다. 이 글에서 다루는 Redis 공식 문서 범위 https://redis.io/docs/latest/develop/get-started/data-store/ https://redis.io/docs/latest/develop/get-started/document-database/ https://redis.io/docs/latest/develop/get-started/vector-database/ Redis 개요 그동안 Redis 를 key-value store, pub/sub 기능으로 써봤음에도 불구하고 막상 Redis 가 무엇이냐는 스스로의 질문에 그 답을 명쾌하게 떠올리지 못했다. 공식 문서에 따르면 Redis 는 “In-memory Data Structure store(인메모리 데이터 구조 저장소)” 라고 한다. 즉, Redis 는 기본적으로 모든 데이터를 Key-Value 구조로 다루면서, Value 에는 문자열 뿐만 아니라 다양한 자료구조(Hash, List,Sorted Set..)를 지원한다. 이 Key-Value 데이터 설계를 근간으로 하며 데이터베이스, 캐시, 메시지 브로커, 스트림의 다양한 역할을 수행하는 엔진이다. 기본 구조 : Key-Value Redis 를 데이터베이스, 캐시, 메시지 브로커, 스트리밍 중 어떤 기능으로 쓰던 간에 Redis 의 모든 데이터는 Key 를 통해 접근한다. Key: 데이터를 식별하는 고유한 이름이다. '바이너리 세이프(Binary Safe)'하여 문자열뿐만 아니라 이진 데이터도 키로 사용할 수 있다. 일반적으로는 콜론(:)으로 구분된 네임스페이스 단위의 문자열 key 를 사용한다. Value: 키에 매핑되는 실제 데이터. 문자열 대신 다양한 자료구조를 담을 수 있다. String: 범용 value container Hash: 하나의 키 안에 여러 필드와 값 쌍을 저장하는 맵 구조. (ex. 사용자 프로필) List: 큐 (ex. 메시지 큐) Set: 순서 없고 중복 없는 집합 (ex. 방문자 IP) Sorted Set (ZSET): 정렬된 Set (ex. 실시간 랭킹) HyperLogLog: 중복을 제거한 서로 다른 값의 개수(cardinality)를 적은 메모리로 근사 계산한 값 (ex. 방문자 수) Geospatial: 위치 인덱스 Stream : append-only 로그 구조의 메시지 스트리밍 데이터 타입 ⇒ Redis Streams 에서 쓰는 데이터 타입이다. Redis의 기능 1. 데이터베이스 (Database) Redis 는 in-memory 기반이지만, Persistence(지속성/영속성) 기능을 제공하기 때문에 데이터베이스로 사용될 수 있다. RDB(스냅샷) 와 AOF(Append Only File) 방식을 통해 Redis memory 의 값을 disk 에 쓴다.(persist) 이를 통해 서버가 재시작되어도 데이터를 복구할 수 있어서 disk DB 의 특성을 가질 수 있다. 당연히 그렇다고 해서 redis 를 disk 기반 DB로 대체해서 쓰라는 뜻은 아니다. 값이 만야 휘발되지 않는다는 뜻이다. 세션 저장소, 실시간 순위표(Sorted Set 활용) 등으로 사용된다. 2. 캐시 (Cache) 데이터가 memory 에 있기 때문에 접근 속도가 disk 기반 DB보다 빠르다. 자주 조회되는 데이터를 Redis 에 저장해두고, 만료 시간(TTL) 설정이나 메모리 관리 정책(Eviction Policy)를 통해 캐시로 활용한다. 메모리 관리(Eviction Policy)는 LRU(Least Recently Used), LFU(Least Frequently Used) 알고리즘을 사용해서 오래됐거나 덜 사용하는 데이터를 삭제한다. 3. 메시지 브로커 (Message Broker) 애플리케이션 간의 비동기 통신을 중개하는 메시지 브로커로 사용된다. Pub/Sub (발행/구독) : UBLISH와 SUBSCRIBE 명령어를 사용하여, 게시자(Publisher)가 특정 채널에 메시지를 보내면 해당 채널을 구독 중인 모든 수신자(Subscriber)에게 실시간으로 메시지를 전달한다. 채팅 시스템이나 실시간 알림에 사용된다. 메시지 큐(Message Queue) : Redis 의 List 자료구조를 활용해 LPUSH(왼쪽삽입), RPOP(오른쪽제거)를 사용하여 큐를 구현할 수 있다. 4. 스트림 (Streams) Redis 5.0부터 도입된 Stream 자료구조를 사용해 대용량 데이터 스트리밍을 처리할 수 있다. Stream 자료구조는 로그 파일처럼 데이터가 추가만 되는(append-only) 구조이다. Consumer Groups 기능으로 여러 Consumer 가 스트림 데이터를 나누어 처리할 수 있다. (Kafka 경량화 버전) 5. 문서 데이터베이스 (Document DB) JSON 자체를 저장하고, 인덱싱 및 빠른 검색을 지원한다. JSON value 를 string으로 직렬화해서 저장하는 방식이 아니라, JSON 형식 문서를 네이티브 JSON 타입으로 저장할 수 있다. Atomic Operations: 문서 전체를 가져와서 수정하고 다시 덮어쓸 필요 없이, JSON.SET이나 JSON.GET과 같은 명령어로 특정 필드 값만 원자적으로 조회하거나 업데이트할 수 있다. Indexing & Full-Text(FT)Search: RediSearch 모듈을 사용해서 JSON 문서 내부의 필드 값을 기준으로 인덱스를 생성하고 고속 검색을 수행할 수 있다 (FT 접두사 명령어) 6. 벡터 데이터베이스 (Vector DB) 데이터베이스 관점에서 Vector 는 데이터의 특징(Feature)를 나타내는 실수 배열이다. 텍스트, 이미지, 비디오 등의 데이터를 벡터 배열로 변환하는 과정을 벡터 임베딩이라 하고, 벡터 임베딩은 임베딩 모델을 통해 수행된다. 벡터 배열은 의미가 비슷한 데이터일수록 벡터 공간에서 서로 가까이 위치한다. Redis 는 이렇게 생성된 벡터 배열을 저장하고, 인덱싱해서 벡터 간 유사도 검색을 지원한다. RAG, AI 어플리케이션에 사용된다.
https://velog.io/@yonghun16/%EB%A0%88%EB%94%94%EC%8A%A4-%EC%8A%A4%ED%8A%B8%EB%A6%BC-Redis-Streams-%EC%9D%B4%EB%9E%80	레디스 스트림 (Redis Streams) 이란?	레디스 스트림 (Redis Streams) 이란? 레디스 스트림(Redis Streams)은 레디스 5.0 버전부터 추가된 강력한 데이터 타입으로, 시간 순서대로 정렬된, 추가만 가능한(append-only) 로그(log) 데이터 구조입니다. 쉽게 말해, 이벤트나 메시지를 발생 순서대로 계속해서 쌓아두고, 여러 클라이언트가 이 데이터 흐름을 읽어갈 수 있게 해주는 기능입니다. 기존의 Pub/Sub(발행/구독) 모델이나 리스트(List)를 이용한 큐 방식의 단점을 보완하여, 더 안정적이고 유연한 메시징 시스템을 구축할 수 있도록 설계되었습니다. 주요 특징: 지속성 (Persistence): Pub/Sub과 달리 스트림에 저장된 데이터는 레디스 메모리에 계속 남아있습니다. 따라서 컨슈머(소비자)가 일시적으로 다운되거나 네트워크 문제가 발생해도 메시지를 유실하지 않고 나중에 다시 읽을 수 있습니다. 시간 순서 보장: 모든 메시지(항목)는 고유한 ID를 가지며, 이 ID는 기본적으로 '타임스탬프-순서'로 구성되어 있어 시간 순서가 보장됩니다. 컨슈머 그룹 (Consumer Groups): 스트림의 가장 강력한 기능 중 하나입니다. 하나의 스트림 데이터를 여러 컨슈머가 협력하여 나눠서 처리할 수 있습니다. 각 컨슈머는 스트림의 다른 부분을 담당하며, 특정 메시지를 누가 처리했는지 추적하고 관리할 수 있습니다. 확인(Acknowledgement) 메커니즘: 컨슈머 그룹을 사용할 때, 컨슈머는 메시지를 성공적으로 처리한 후 '처리 완료' 신호(ACK)를 보낼 수 있습니다. 이를 통해 메시지 처리의 신뢰성을 높이고, 처리 중 문제가 생긴 메시지를 다른 컨슈머가 다시 처리하도록 할 수 있습니다. 간단한 사용법 (redis-cli 예제) 레디스 스트림은 주로 XADD, XREAD, XGROUP, XREADGROUP 등의 명령어를 통해 사용됩니다. redis-cli를 통해 직접 체험해보는 것이 가장 이해하기 쉽습니다. 1. 데이터 추가하기: XADD 스트림에 새로운 메시지(항목)를 추가합니다. 명령어 형식: XADD [스트림 키] [ID] [필드1] [값1] [필드2] [값2] ... ID: *: 레디스가 자동으로 '타임스탬프-순서' 기반의 ID를 생성해줍니다. (가장 일반적인 방법) 직접 지정: 1662500000-0 와 같이 직접 ID를 지정할 수도 있습니다. 필드-값: 메시지는 하나 이상의 필드-값 쌍으로 구성됩니다. 예제: mystream이라는 이름의 스트림에 사용자 정보와 메시지를 추가해 보겠습니다. redis-cli 127.0.0.1:6379> XADD mystream * user "user:123" message "hello" "1724612080398-0" 127.0.0.1:6379> XADD mystream * user "user:456" message "world" "1724612095123-0" 2. 데이터 읽기 (개별 컨슈머): XREAD 스트림에서 메시지를 읽습니다. 마지막으로 읽은 ID를 기억하고 있다가 그 다음부터 읽어오는 방식으로 실시간 스트리밍을 구현할 수 있습니다. 명령어 형식: XREAD [COUNT 개수] [BLOCK 밀리초] STREAMS [스트림 키1] [스트림 키2] ... [ID1] [ID2] ... COUNT: 한 번에 가져올 메시지의 최대 개수 BLOCK: 새로운 메시지가 들어올 때까지 대기할 시간 (0은 무한 대기) ID: 0-0: 처음부터 모든 메시지를 읽어옵니다. $: 현재 스트림의 마지막 메시지 다음부터 들어오는 새로운 메시지를 기다립니다. 특정 ID: 해당 ID 다음부터 메시지를 읽어옵니다. 예제: 127.0.0.1:6379> XREAD STREAMS mystream 0-0 1) 1) "mystream" 2) 1) 1) "1724612080398-0" 2) 1) "user" 2) "user:123" 3) "message" 4) "hello" 2) 1) "1724612095123-0" 2) 1) "user" 2) "user:456" 3) "message" 4) "world" 127.0.0.1:6379> XREAD BLOCK 0 STREAMS mystream $ 3. 컨슈머 그룹 사용하기 여러 컨슈머가 협력하여 메시지를 처리하는 강력한 방법입니다. 3.1. 컨슈머 그룹 생성: XGROUP CREATE 명령어 형식: XGROUP CREATE [스트림 키] [그룹 이름] [ID] [MKSTREAM] ID: 0-0: 스트림의 처음부터 모든 메시지를 처리 대상으로 합니다. $: 그룹 생성 이후에 들어오는 새로운 메시지만 처리 대상으로 합니다. MKSTREAM: 스트림이 존재하지 않을 경우 자동으로 생성합니다. 예제: mystream을 처리할 mygroup이라는 컨슈머 그룹을 생성합니다. 127.0.0.1:6379> XGROUP CREATE mystream mygroup 0-0 OK 3.2. 그룹으로 데이터 읽기: XREADGROUP 그룹에 속한 컨슈머가 자신에게 할당된 메시지를 읽어옵니다. 명령어 형식: XREADGROUP GROUP [그룹 이름] [컨슈머 이름] [COUNT 개수] [BLOCK 밀리초] STREAMS [스트림 키] [ID] 컨슈머 이름: 메시지를 읽어가는 주체(애플리케이션 인스턴스 등)를 식별하는 임의의 이름 ID: >: 아직 그룹 내 어떤 컨슈머에게도 전달되지 않은 새로운 메시지를 요청합니다. (가장 일반적) 0-0: 처리되었지만 아직 ACK를 받지 못한 '대기 중인(pending)' 메시지를 다시 읽어옵니다. (장애 복구 시 사용) 예제: 컨슈머 'consumer-1'과 'consumer-2'가 번갈아 메시지를 가져가는 상황입니다. 127.0.0.1:6379> XREADGROUP GROUP mygroup consumer-1 COUNT 1 STREAMS mystream > 1) 1) "mystream" 2) 1) 1) "1724612080398-0" 2) 1) "user" 2) "user:123" 3) "message" 4) "hello" 127.0.0.1:6379> XREADGROUP GROUP mygroup consumer-2 COUNT 1 STREAMS mystream > 1) 1) "mystream" 2) 1) 1) "1724612095123-0" 2) 1) "user" 2) "user:456" 3) "message" 4) "world" 3.3. 처리 완료 알리기: XACK 컨슈머가 메시지 처리를 성공적으로 마쳤다고 그룹에 알립니다. ACK를 해야 해당 메시지가 '대기 중인 메시지 목록(Pending Entries List, PEL)'에서 제거됩니다. 명령어 형식: XACK [스트림 키] [그룹 이름] [ID1] [ID2] ... 예제: consumer-1이 처리한 메시지에 대해 ACK를 보냅니다. 127.0.0.1:6379> XACK mystream mygroup "1724612080398-0" (integer) 1 이처럼 레디스 스트림을 사용하면 간단한 채팅, 이벤트 큐, 작업 큐, 실시간 데이터 파이프라인 등 다양한 애플리케이션을 안정적으로 구축할 수 있습니다.
