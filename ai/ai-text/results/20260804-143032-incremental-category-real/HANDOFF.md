# 증분 카테고리 서비스 (실제 모드) — 결과 해석 & 테스트 설계 핸드오프

이 문서 하나로 결과 해석과 다음 테스트 설계가 가능하도록 정리했다. 원본 수치는
같은 폴더의 `run-summary.json`, `comparison-report.md`, `<순서>/report.md`,
`<순서>/items.csv`, `<순서>/candidates.csv`에 있다.

## 1. 이 실행이 무엇인가

- 실제 서비스처럼 데이터를 **한 건씩** 입력하는 증분 카테고리 엔진.
- 데이터 112건(정우현 URL 데이터셋)을 `original / shuffle-42 / shuffle-84`
  **세 순서**로 각각 처음부터 처리.
- **모드: real** — 임베딩은 GMS `text-embedding-3-small`, 정식 분류·후보 필요
  판단·이름/설명 생성·승격 검토는 OpenRouter `qwen/qwen3-8b`. **API 에러 0건으로
  완주**했다(모든 데이터의 `candidateError`가 비어 있음).

## 2. 설정값 (config/incremental-category.yaml)

| 키 | 값 |
|---|---|
| max-count | 10 |
| max-ai-generated-count | 5 |
| formal-confidence-threshold | 0.65 |
| formal-score-gap-threshold | 0.10 |
| candidate-similarity-threshold | 0.80 |
| candidate-min-support-count | 3 |
| service-max-categories | 2 |

## 3. 결과 요약 (세 순서)

| 순서 | 애매 판정 | 평균 최고점수 | 최종 정식 | AI 승격 | 생성 후보 | 후보 재사용 | 1건 후보 | 재분류 | 10개 초과 |
|---|--:|--:|--:|--:|--:|--:|--:|--:|:--:|
| original | 11/112 | 0.883 | 5 | 0 | 9 | 2 | 7 | 0 | 아니오 |
| shuffle-42 | 16/112 | 0.863 | 6 | 1 | 12 | 2 | 9 | 3 | 아니오 |
| shuffle-84 | 13/112 | 0.871 | 5 | 0 | 12 | 1 | 11 | 0 | 아니오 |

- 승격은 **shuffle-42에서 단 1건**(`심리·자기성찰`, 연결 3건, URL-016 최초). 나머지
  두 순서는 승격 0.
- 112건 대부분이 5개 시드 카테고리에 배치됨. 예) original 시드 데이터 수:
  생활·건강 22, 학습·커리어 27, 장소·먹거리 20, 소비·금융 25, 문화·아이디어 18.

## 4. 핵심 발견 (해석)

1. **실제 분류는 매우 확신적이다 → 후보 파이프라인이 거의 안 열린다.**
   평균 최고 점수가 0.86~0.88로 임계값 0.65를 크게 웃돈다. 그래서 "애매"로
   분류돼 후보 단계로 넘어간 데이터가 순서당 11~16건(약 10~14%)뿐이다. 나머지
   ~86%는 5개 시드로 바로 분류됐다.

2. **의미가 같은 후보가 서로 다른 이름으로 쪼개져 승격이 억제된다 (가장 중요).**
   실제 AI가 이름은 잘 짓지만 같은 주제에 조금씩 다른 이름을 붙였고,
   `candidate-similarity-threshold=0.80`이 이들을 병합하지 못했다. 증거:

   | 주제 | original | shuffle-42 |
   |---|---|---|
   | 운세 | 운세·예측(1) + 운세 정보(1) | 운세·타로(1) + 운세·예측(2) |
   | 심리/자기 | 심리·자기개발(2) + 자기성찰(1) | 심리·자기성찰(3, 승격) + 자기 이해(1) + 심리검사(1) |
   | 앱/디지털 | 앱·서비스(2) + 기술·하드웨어(1) + 디지털 플랫폼(1) | 앱·디지털(2) + 기술·하드웨어(1) + 콘텐츠 플랫폼(1) + 실용 디자인(1) |
   | 사회공헌 | 커뮤니티·공유(1) + 사회공헌(1) | 사회공헌(1) + 공동체·기여(1) |

   각 주제의 데이터가 합쳐졌으면 support 3~5로 승격됐을 텐데, 이름이 갈리며
   support 1~2에 머물러 대부분 승격 문턱(3)을 못 넘었다. shuffle-42에서 심리
   주제만 우연히 한 후보로 3건이 모여 유일하게 승격됐다.

3. **순서 민감도가 크다.** 같은 데이터·설정인데 승격 수가 0/1/0으로 갈렸다.
   먼저 온 데이터가 어떤 이름의 후보를 선점하느냐에 결과가 좌우된다(발견 2와
   맞물림).

4. **엔진 메커니즘은 설계대로 동작.** 정식 상한 10 준수(초과 0), API 실패 격리
   (에러 0), 승격 시 재분류(shuffle-42 3건) 정상.

### 신뢰 구분
- **신뢰 가능(실측)**: 애매 판정 비율(~10~14%), 평균 분류 확신도(0.86~0.88),
  후보 파편화 현상, 순서 민감도, 상한/실패 처리.
- **주의**: 절대 승격 수(0~1)는 "서비스에서 카테고리가 거의 안 는다"는 최종
  결론이 아니라 **현재 임계값 조합의 결과**다. 특히 발견 2(후보 병합 부재)를
  고치면 승격 수가 오를 가능성이 높다.

## 5. 추후 테스트 설계 제안 (우선순위 순)

A. **후보 병합/이름 정규화 도입 후 재측정 (최우선, 발견 2 대응)**
   - 가설: 같은 주제의 이름 변형을 병합하면 support가 합쳐져 승격이 늘어난다.
   - 실험: (a) `candidate-similarity-threshold`를 0.80 → 0.70/0.65로 낮춰 스윕,
     (b) 이름 토큰 겹침 기반 병합(운세·예측 ↔ 운세·타로) 추가, (c) 후보 생성 시
     기존 후보 설명까지 AI에게 보여주고 "새로 만들지/기존에 붙일지" 판단시키기.
   - 지표: 주제당 후보 수(파편화 정도), 승격 수, 승격된 카테고리의 응집도.

B. **애매 판정 임계값 스윕 (발견 1 대응)**
   - 후보 파이프라인 유입량을 조절: `formal-confidence-threshold`(0.65→0.70/0.75),
     `formal-score-gap-threshold`(0.10→0.15). 유입이 늘면 신규 주제 포착↑,
     대신 오분류·과생성 위험↑. 트레이드오프 곡선을 그린다.

C. **min-support 조정**
   - 112건 규모에서 support 3은 높을 수 있다. 2로 낮췄을 때 승격 수·정밀도 변화
     측정(과잉 승격 위험과 함께).

D. **승격 정밀도(품질) 평가**
   - 승격된 카테고리(예: 심리·자기성찰)의 연결 데이터가 실제 한 주제인지 사람이
     검수. 목적이 섞였는데 승격된 오승격 사례 집계.

E. **순서 강건성 확대**
   - shuffle 시드를 5~10개로 늘려, 최종 정식 카테고리 집합의 안정성(자카드),
     특정 주제(심리/운세/앱)의 승격 재현율을 측정. 발견 3의 정량화.

F. **정답 라벨 기반 정식 분류 정확도**
   - 데이터셋 정답(폴더명)과 시드 5개 배치 결과를 대조해 Top-1/relaxed 정확도.
     시드 5개가 이 데이터셋을 얼마나 커버하는지 확인(발견 1의 원인 규명).

G. **데이터 규모 확대**
   - 후보 승격은 반복 주제가 충분히 쌓여야 나타난다. 112건은 주제당 데이터가
     적다. 더 큰 데이터셋(또는 특정 주제 집중 데이터)에서 재측정.
